## 背景

shipping 团队每天要手动翻几百条订单，找出哪些可以合一起发——同一个账号、同一个 ZIP code，能拼一箱就拼。问题在于仓库抓货时间不固定，订单还有 7 天的发货窗口限制，追踪表又是多人实时编辑的。信息都在，就是太分散了。

## 做了什么

一个 Python 脚本，每天运行一次，从两个地方拉数据，把合单建议直接写进 Google Sheet 的 Note 列——只追加，不覆盖人工写的内容。

数据来源：

- **Google Sheets**（`gspread`）—— 团队的主订单追踪表
- **NetSuite Item Fulfillments 导出**（`.xls`）—— 当天的仓库抓货记录

脚本把两份数据对照，按账号 + ZIP 分组，走一套合并规则，标出可以拼单的订单。

## 合并逻辑

两张单满足以下条件才能合并：

- `ACCT#` 和 `ZIP CODE` 相同
- 状态是 `stock order`、`hold`、`FcsRepleshing`，或者今天的 `send`
- 预计发货日相差 ≤ 3 天，**或者**仓库抓货日期相差 ≤ 3 天

一个边界情况处理起来比较麻烦：如果组里有一张单已经抓货了，另一张没有，而且没抓的那张 QTY > 300——这对就直接放弃合并，单独发一个警告。大单抓货时间太长，等它不划算。

三张或以上的单，脚本先按兼容性建图（两张单通过时间窗口检查则连一条边），然后在图里找"任意两张都互相满足条件"的子集。

具体算法是贪心迭代最大团：枚举所有剩余节点作为起点，从每个起点出发贪心展开——新成员必须与当前团内所有节点都有边才能加入——取所有起点里找到的最大团，提交后从池里移除，再找下一个不重叠的团。

没有用 Bron-Kerbosch。B-K 通过递归 + 回溯 + P/R/X 三个集合的维护，保证找到所有极大团，理论上完备。但它的优势只在图足够大、边的结构足够复杂时才体现出来。这个脚本里每组最多 2-4 张单——同账号、同 ZIP、还要在 3 天窗口内——贪心方案在这个规模下和 B-K 得到完全相同的结果，代码却简单得多，不熟悉图算法的人也能看懂在做什么。

一个实现细节：触发大单排除条件的 SO 会在建组之前就从所有边里移除，放进 `excluded_from_merge` 集合。如果不做这一步，被排除的单还是可能通过别的路径混进某个小团里。

## 数据流

```
NetSuite .xls 导出（38,000+ 行）
        ↓ 先过滤出追踪表里有的 SO（约 293 条）
IF_history tab（Google Sheet）
        ↓ 按 so_norm::if_doc 作为唯一 key upsert
追踪表分析
        ↓ clique 分组 + 排除规则
Note 列写回（只追加，保留人工内容）
```

NetSuite 导出包含一个月内所有客户的仓库记录，大概 38,000 行，大部分跟当前追踪表无关。约 293 这个数字来自过滤：把 IF 表里所有记录的 SO 编号和追踪表里当前有效的 SO 集合对比，只保留匹配的那些写进 `IF_history`。这样历史表体量小，API 调用也不超限。

写回用 `[自动]` 标签区分自动内容和人工内容，每次运行只刷新标签后面的部分，标签前的人工内容不动。

## 踩过的坑

NetSuite 导出的 `.xls` 实际上是 SpreadsheetML XML，`pandas.read_excel` 处理不了，得用 `xml.etree.ElementTree` 手动解析。

Google Sheets API 有写入频率限制，一开始没过滤直接写 38,000 行，立刻 429 了。改成先过滤再写入，降到几百行，就没事了。

追踪表表头在第 3 行，数据从第 4 行开始，`get_all_records()` 会因为空列头报错。改成 `get_all_values()` 加固定列名映射解决。

Google Sheets 会把 `00968` 这种 ZIP code 当数字处理，读出来就变成 `968` 了。读取后加 `zfill(5)` 补回来。


## 如果重来

Clique 检测贪心展开不回溯，每组 2-4 张单时结果和精确解一致。如果未来某天某个账号同时有十几张单都满足合并条件，贪心方案理论上可能漏掉真正的最大团。届时换成 Bron-Kerbosch 会更可靠，代价是逻辑更难维护。

IF_history 的清理是逐行删除，如果一次性有很多 SO 失效会比较慢，改成批量删除更稳。

日志现在全是 `print`，出问题只能重跑脚本去看。写到文件里会省事很多。
